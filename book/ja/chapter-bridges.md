# DeepRail Chapter Bridges / Closing

## Chapter Bridges

> **Purpose:** Chapter Bridgeは章の要約ではない。いま理解したことを、次に解くべき問いへ変換する。読者を「章が終わった」状態に置かず、視点の焦点距離を一段だけ動かす。
>
#### Part I — AIが働く時代を理解する

**Ch1 → Ch2**  
AIの使い方だけを見ているうちは、まだToolの話で済む。仕事そのものを任せ始めたとき、AIはいつまで「便利な道具」のままでいられるのか。

**Ch2 → Ch3**  
AIが出力を作るだけでなく、調査し、実行し、判断候補まで持つようになると、従来の役割分担は揺れ始める。次に見るべきなのは、HumanとAIの境界そのものだ。

**Ch3 → Ch4**  
境界が動くなら、仕事の配分だけでは済まない。誰に人を置き、何に投資し、どのDecision Rightsを移すかという経営の問題が立ち上がる。

**Ch4 → Ch5**  
会社の設計を変える前に、一人ひとりの働き方も変わる。AI時代のSkillは、上手に作業することより、何を任せ、何を確かめ、何を学習へ戻すかへ移っていく。

**Ch5 → Ch6**  
しかし、委譲が上手な個人だけでは組織は強くならない。個人の判断を支えるPurpose、Rule、権限、評価、学習がつながったとき、HarnessとOrganizationの似た形が見えてくる。

**Ch6 → Ch7**  
似ていると分かっただけでは会社は変わらない。次は、その構造を現実の役割、権限、Processへ落としたOperating Modelを考える。

#### Part II — AIが働ける組織へ変える

**Ch7 → Ch8**  
理想のOperating Modelを描いても、現在地を無視すれば導入は止まる。同じ設計でも、GreenfieldとLegacyでは動かし方が違う。

**Ch8 → Ch9**  
現在地を見れば、技術以外の壁が見えてくる。Data、Security、契約、Network、IAM。AI Native化は、Repositoryの中だけでは完結しない。

**Ch9 → Ch10**  
制約を並べるだけでは前へ進まない。誰が例外を決め、誰がRiskを引き受け、誰がGOを出せるのか。制約の次にはDecision Rightsがある。

**Ch10 → Ch11**  
DecisionのOwnerが見えたら、初めて小さく試せる。問題はPoCを成功させることではなく、その成功をどう標準化し、どこまで広げるかである。

**Ch11 → Ch12**  
仕組みを配っても、人が仕事を任せられなければ広がらない。次の論点はToolの習熟ではなく、委譲・評価・改善を学べる人材をどう増やすかだ。

**Ch12 → Ch13**  
委譲は講義だけでは身につきにくい。自分で一度、要求からReleaseまでを通り、摩擦からRuleやTestの必要性を発見したとき、Harnessは知識ではなく経験になる。

**Ch13 → Ch14**  
一人でEnd-to-Endを回せるようになったら、次の問いはもっと手前にある。そもそも、その仕事はどこから生まれ、何をOutcomeと呼ぶのか。

#### Part III — 顧客の要求をAIが働ける仕事へ変える

**Ch14 → Ch15**  
Demandが届いた時点では、まだ正しい仕事とは限らない。依頼の言葉の奥にあるProblemを発見できなければ、AIは間違った要求まで速く実装する。

**Ch15 → Ch16**  
Problemが見えても、頭の中だけでは認識は揃わない。曖昧な理解をScenario、画面、Modelのような見えるものへ出す必要がある。

**Ch16 → Ch17**  
見える形を作ることと、同じ意味で見ていることは違う。次は、そのArtifactを使って認識差を表面へ出す。

**Ch17 → Ch18**  
Alignmentは、全員が何でも合意することではない。何を今決め、何をUnknownとして残すかを切り分けて初めて仕事は前へ進む。

**Ch18 → Ch19**  
決めたことが会議の記憶に残るだけでは、AIは実行できない。DecisionをAcceptance、Constraint、Evidenceへ変え、実行可能な契約にする。

**Ch19 → Ch20**  
契約ができても、そのまま大きな仕事を一つのAgentへ渡せるとは限らない。次は、独立して任せ、確かめ、やり直せる単位へ仕事を分ける。

**Ch20 → Ch21**  
Task一覧ができても、仕事はまだ流れていない。分けた仕事がHumanとAIの間をどう動き、誰が何を決めるのか。ここからTeam設計へ入る。

#### Part IV — Human + AI Teamを運営する

**Ch21 → Ch22**  
Teamの役割を置いただけでは自律は生まれない。目的、Flow、例外、Decisionを誰かが設計し続ける必要がある。その機能がAI時代のLeadershipになる。

**Ch22 → Ch23**  
Leadershipは肩書きではなく、日々のDecisionに現れる。会議を情報共有の場から、何を決め何を残すかを更新する場へ変えていく。

**Ch23 → Ch24**  
良いDecisionができても、仕事を無制限に流せば詰まる。AIが増えるほど、WIP、依存、Environment、Review Capacityを含むFlowを見る必要がある。

**Ch24 → Ch25**  
Flowを見ていると、結局一つの問いに戻る。どの仕事をどこまでAIへ任せ、どこから先を止めるのか。その境界は固定できない。

**Ch25 → Ch26**  
任せる範囲を広げるほど、最後に必要になるのは成果をどう確かめるかである。Human Reviewを「全部読む作業」から判断のInterfaceへ変える。

**Ch26 → Ch27**  
人間がEvidenceで判断できるようになったら、次の問いが生まれる。その評価自体を、どのWork ClassならAIへ委譲できるのか。

**Ch27 → Ch28**  
ExecutionとEvaluationの権限を分けて設計できるようになると、個別Taskだけでなく開発全体の流れを組み替えられる。ここからSoftware Engineeringへズームインする。

#### Part V — AI Native Software Engineering

**Ch28 → Ch29**  
Lifecycleを決めても、AIの仕事が一度で正解に着地するとは限らない。Retry、Re-plan、再分解まで最初からProcessに入れておく。

**Ch29 → Ch30**  
Loopを回すことと、特定の開発手法を信仰することは違う。Agile、Waterfall、Hybridの名前より、どこでFeedbackを得られるかを見る。

**Ch30 → Ch31**  
同じProcessを全案件へ当てる理由はない。Risk、規模、Reversibility、Autonomy、Operating Contextが変われば、適切な設計も変わる。

**Ch31 → Ch32**  
Operating Contextが決まると、次は変更をどこで隔離し、何をSource of Truthにし、誰のWorkと衝突させないかが具体的な問題になる。

**Ch32 → Ch33**  
理想的なRepository構成だけを前提にすると、現実の会社では止まる。Legacy、Centralized VCS、既存Issue管理、複数Repositoryの制約の中でも原則を成立させる必要がある。

**Ch33 → Ch34**  
Repositoryが新しくても古くても、変更を安全に前へ運ぶ背骨は必要だ。ここから焦点を、Codeを書く場所からDelivery Systemへ移す。

#### Part VI — Delivery Systemを設計する

**Ch34 → Ch35**  
CI/CDは変更を運べる。しかし、運べることと正しいことは同じではない。次は、何を証明したらGateを越えてよいかを設計する。

**Ch35 → Ch36**  
Test結果だけを見ても、そのEvidenceがどのEnvironment、Version、Dataで得られたか分からなければ再利用できない。状態そのものがEvidenceの一部になる。

**Ch36 → Ch37**  
再現可能なEnvironment Evidenceが揃っても、最後はProductionという別のRealityに出る。Release、観測、Rollbackまで含めてOutcomeを完了させる。

**Ch37 → Ch38**  
Releaseできたことは一つの終点だが、組織にとっては次の始点でもある。失敗とEvidenceを、次のExecutionが変わる形へ戻さなければ同じ摩擦を繰り返す。

**Ch38 → Ch39**  
Rule、Test、Gate、Contextへ学びを戻し続けると、いつの間にか一つの実行系ができている。ここで初めて、Harness Engineeringを独立した設計対象として見る意味が出てくる。

#### Part VII — Execution Harnessの最深部へ

**Ch39 → Ch40**  
Harnessは、仕事を成立させるための工夫が積み重なって今の形になった。設計するときも、部品一覧から眺めるよりDeliveryのFailureから辿る方が分かりやすい。

**Ch40 → Ch41**  
Deliveryから逆算しても、AIが必要なRealityを見られなければ実行は崩れる。次はContextを、量ではなく仕事に必要な認識状態として設計する。

**Ch41 → Ch42**  
Contextだけでは行動は安定しない。何を守り、何を再利用し、どこで止めるかをRule、Skill、Agent、Hookへ分けて配置する。

**Ch42 → Ch43**  
構成要素を置いたら、それらが何を使って動くかが問題になる。Model、Tool、Runtime、Permissionまで含めてExecution Contractを閉じる。

**Ch43 → Ch44**  
実行系ができても、それ自体が正しいとは限らない。GuardもEvalも壊れる。Harness自身を観測し、変え、時には削除する仕組みが必要になる。

**Ch44 → Ch45**  
HarnessがExecution Evidenceから学び、自分を更新し始めると、話は再び会社へ戻る。個々のRepositoryの改善を、どう組織の判断とStrategyへ返すのか。

#### Part VIII — Organization Engineeringへ戻る

**Ch45 → 終章**  
Organization Engineeringまで来ると、AI Native化を開発部門だけの新しいやり方とは呼びにくくなる。最後に残るのは、仕事を任せる一人ひとりが、どんな責務配置を作るのかという問いだ。

#### 終章 — 小さな組織を率いる

最初は、AIに一つの仕事を頼むだけだった。

調べてもらう。文章を書いてもらう。コードを書いてもらう。そこまでは、便利なToolの延長に見える。

けれど、任せる仕事が少し大きくなると事情が変わる。何を目的とするかを決めなければならない。仕事を分けなければならない。どこまで決めてよいかを渡さなければならない。成果を確かめ、例外を判断し、失敗から次の仕組みを変えなければならない。

これは、AI操作の話だけではない。

**小さな組織を運営している。**

しかも、その組織図は固定されない。今日Humanが担っているReviewを、明日はAIがEvidence付きで担うかもしれない。PlanningもCoordinationもStrategy Option Designも、能力と条件が揃えば境界の内側へ入ってくる。

だから守るべきなのは「人間の仕事」ではない。

守るべきなのは、責務が動いても仕事が成立する条件である。目的が見えること。権限が分かること。Evidenceで確かめられること。止まれること。戻せること。そして、失敗が次のExecutionを変えること。

ここまで追ってきたのは、AIの操作方法より、そのAIに仕事を任せても仕事が壊れない条件だった。

**AIが働く世界で、仕事そのものを設計し直せる人と組織を増やしたい。**

AIへ仕事を任せるたびに、そこには小さな組織が生まれる。

その組織をどう設計するかは、もう一部の経営者だけの仕事ではない。
